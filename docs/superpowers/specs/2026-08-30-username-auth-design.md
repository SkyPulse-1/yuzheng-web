# 语证用户名认证与多设备同步设计

## 目标

用户无需提供邮箱或手机号，只使用唯一用户名和密码注册、登录语证。同一账号可以在多台设备登录，并访问同一套知识库、文档、会话和证据卡。忘记密码时使用注册阶段生成的恢复码设置新密码。

## 用户体验

### 注册

注册表单仅包含用户名、密码和确认密码。注册成功后，系统显示一条只展示一次的恢复码，并要求用户复制或下载保存。用户确认已保存后进入 Dashboard。

用户名长度为 3–24 位，只允许英文字母、数字和下划线。用户名不区分大小写，并以小写形式保存；`SkyPulse` 与 `skypulse` 视为同一用户名。显示名称不属于本轮范围。

### 登录

登录表单仅显示用户名和密码。失败时统一提示“用户名或密码错误”，不说明用户名是否存在。登录成功后由 Supabase 建立会话并进入 Dashboard。

### 找回密码

找回表单包含用户名、恢复码、新密码和确认密码。恢复成功后旧恢复码立即失效，系统生成一条新恢复码。连续失败会触发短时锁定，避免暴力尝试。

## 认证架构

Supabase Auth 原生密码身份使用邮箱或手机号，因此语证在服务端为每个规范化用户名计算一个不可见的内部邮箱标识。计算使用服务端 `USERNAME_AUTH_SECRET` 和 HMAC-SHA256，结果形如 `u_<digest>@auth.yuzheng.invalid`。浏览器、界面、日志和业务数据均不显示该标识。

注册和登录只通过 Next.js 服务端操作完成：

1. 服务端校验并规范化用户名。
2. 服务端计算内部邮箱标识。
3. 注册调用 Supabase `signUp`，并在用户元数据中提交规范化用户名。
4. 登录调用 Supabase `signInWithPassword`。
5. Supabase 返回的用户 UUID 继续作为所有业务表的 `owner_id`。

Supabase 项目必须关闭内部邮箱身份的确认邮件，因为内部邮箱不可接收邮件。系统不提供邮件链接登录。

## 数据模型

新增 `public.profiles`：

- `id uuid primary key references auth.users(id) on delete cascade`
- `username text not null`
- `username_normalized text not null unique`
- `created_at timestamptz`
- `updated_at timestamptz`

新增 `public.account_recovery`：

- `user_id uuid primary key references auth.users(id) on delete cascade`
- `recovery_digest text not null`
- `failed_attempts integer not null default 0`
- `locked_until timestamptz`
- `rotated_at timestamptz`

`profiles` 允许登录用户读取自己的记录，不允许客户端直接修改用户名。`account_recovery` 不开放给普通客户端，只由持有 Supabase 服务端密钥的代码访问。

注册触发器从新用户元数据读取用户名并写入 `profiles`。数据库唯一约束是用户名唯一性的最终保障；并发注册同名账号时只有一个事务成功。

## 恢复码

恢复码使用加密安全随机数生成，展示格式采用分组字符，便于人工保存。数据库只保存通过 `ACCOUNT_RECOVERY_SECRET` 计算的 HMAC-SHA256 摘要，不保存明文。

恢复接口使用服务端 Supabase 密钥查找用户和更新密码。连续 5 次错误后锁定 15 分钟。恢复成功后清零失败次数、更新密码、撤销旧恢复码并生成新恢复码。服务端密钥和恢复密钥只存放在未提交 Git 的环境变量中。

## 多设备同步

同一用户名始终映射到同一个 Supabase 用户 UUID。每台设备登录后获得独立会话，但所有业务查询都通过相同的 `auth.uid()` 和现有 RLS 策略访问数据。因此知识库、文档、聊天记录和证据卡天然共享，不需要额外同步服务。

默认允许一个账号存在多个活跃设备会话，不启用“单会话限制”。任意设备上的新增、编辑和删除会作用于同一份云端数据。

## 现有账号兼容

现有邮箱账号和数据不得删除或重建。为已登录的旧账号提供一次性“设置用户名”入口：

1. 用户输入尚未占用的用户名，并设置新密码。
2. 服务端为当前用户写入 `profiles` 和恢复码。
3. 服务端通过管理接口将内部邮箱身份和新密码设置为后续用户名登录凭据。
4. 原有用户 UUID 保持不变，因此所有历史数据继续可见。

如果旧账号无法完成登录，迁移只能由管理员在确认账号归属后执行，不允许仅凭原邮箱文字声明迁移。

## 安全与错误处理

- 密码至少 8 位；生产环境应启用 Supabase 密码强度与泄露密码检查。
- 所有认证操作均在服务端执行，内部邮箱算法与管理密钥不下发浏览器。
- 注册、登录和恢复接口设置请求频率限制。
- 登录错误不区分用户名不存在或密码错误。
- 恢复码错误不返回剩余尝试次数之外的账号信息。
- 日志不得记录密码、恢复码、内部邮箱、会话令牌或服务端密钥。
- 注册过程任一步失败都不显示成功状态。

## 配置

新增服务器环境变量：

- `SUPABASE_SECRET_KEY`
- `USERNAME_AUTH_SECRET`
- `ACCOUNT_RECOVERY_SECRET`

这些变量只存在于本地 `.env.local` 和未来部署平台的加密环境变量中，不提交 Git。

## 测试与验收

- 大小写不同但规范化结果相同的用户名不能重复注册。
- 并发注册相同用户名时只有一个成功。
- 用户名和密码可在两台独立浏览器中登录同一用户 UUID。
- 一台设备创建的知识库能在另一台设备刷新后看到。
- 错误用户名和错误密码返回相同提示。
- 正确恢复码可以修改密码，旧密码和旧恢复码随后失效。
- 连续 5 次错误恢复尝试触发 15 分钟锁定。
- 旧账号完成迁移后用户 UUID 与历史数据保持不变。
- `npm run lint`、`npm run build` 和认证路由测试通过。

## 本轮不包含

本轮不加入邮箱、手机号、OAuth、短信验证码、MFA、显示名称修改或账号合并。Vercel 部署和 HiAgent、VikingDB 联调保持原计划，不与认证改造混合实施。
